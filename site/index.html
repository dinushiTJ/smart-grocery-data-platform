Smart Grocery Data Lakehouse

A grocery price pipeline that shows its working.

It pulls real product data, invents supermarket prices for it, then checks every single record before letting it into the warehouse, and keeps a permanent, queryable record of everything it threw away and why.

03

The pipeline, stage by stage

Ten stages, in the order you would run them on a fresh machine. The first eight are the warehouse route; the last two are the streaming one, and are optional.

01

Set up the warehouse

One Postgres database holds all four layers, each in its own schema. Metabase runs next to it for the dashboards.

docker compose up -d
Under the hood
  • The schema files only run once sql/ is mounted into the container's init directory, which Postgres executes only when the data volume is empty. Editing sql/001_create_database.sql does nothing to a database that already exists. Apply the change by hand or recreate the volume.
  • Indexes are manual sql/indexes.sql has no number prefix, so it never runs automatically. See docs/query-performance.md for the before/after measurement.
02

Fetch the products

A sample of beverages is pulled from Open Food Facts, a real public food database, and written to a timestamped file. Nothing is cleaned yet.

python3 ingestion/extract_products.py
Under the hood
  • Files are the handoff Each script writes data/bronze/…/<name>_<timestamp>.json|csv and the next stage finds its input with find_latest_file(), literally sorted(glob)[-1]. The timestamp in the filename is load-bearing; rename a file and the pipeline picks up the wrong one.
03

Invent the prices

Open Food Facts has no prices, so the platform generates them for five fictional New Zealand supermarkets, and deliberately corrupts a slice of them.

python3 ingestion/generate_prices.py
Under the hood
  • The bad data is on purpose generate_prices.py injects four faults, each at roughly 2%: a negative price, an empty price, an unknown store, and a barcode that matches no product. Without them the quarantine path would never run and the data-quality dashboard would be an empty page.
  • Every row shares one timestamp The generator stamps datetime.now() per row inside a loop that finishes in milliseconds, so an entire run occupies a single instant. That is why nothing here shows price movement over time.
04

Clean, check and load

The one job that does the real work: read the raw files, judge every record, load what passes into silver and file what fails into quarantine with a reason.

python3 -m processing.run_pipeline
Under the hood
  • Run it as a module, not a path It imports quality.semantic_validation, so python3 processing/run_pipeline.py fails on the import. The -m form is required.
  • A run is always accounted for The run row is written as RUNNING on its own connection and committed immediately, so a crash still leaves a visible record. The whole body is wrapped so a run ends as either SUCCESS with counts or FAILED with the error message.
  • Rejecting a product removes its prices If a product fails, any prices already loaded against its barcode are deleted first, then the product (foreign keys make the order mandatory), and the original record is quarantined.
05

Check it four ways

Validation is layered rather than a single gate, so a structural problem and a nonsense product name are caught by different things.

Under the hood
  • What actually runs Deterministic rules in quality/semantic_validation.py run inside the pipeline and are authoritative. An optional local LLM review runs on top only when OLLAMA_SEMANTIC_VALIDATION is set, and it can never overturn a deterministic reject. dbt tests check the warehouse output after the fact.
  • What does not run yet The Great Expectations suites in quality/product_expectations.py and quality/price_expectations.py are written but have no __main__ block and no caller, so nothing invokes them. quality/quality_rules.yml is a written catalogue of those expectations, not executed configuration. Both are honest gaps, not hidden ones.
06

Model it with dbt

SQL transformations that live in version control and carry their own tests, instead of a query someone saved in a BI tool.

cd grocery_dbt && dbt run && dbt test
Under the hood
  • It reads silver as a source daily_price_summary goes through sources.yml rather than ref(), because the silver tables are loaded by Python, not built by dbt. The connection profile lives outside the repo in ~/.dbt/profiles.yml.
07

Schedule it

Airflow runs the same three commands once a day, in order, with retries. It is the manual walkthrough above, automated.

cd airflow_local && docker compose up airflow-init && docker compose up -d
Under the hood
  • A second Compose project Airflow is not a service in the root compose.yaml; it is its own stack in airflow_local/, on localhost:8080. It reaches the warehouse over host.docker.internal and expects the repo mounted at /opt/smart-grocery.
  • The DAG is the same three steps extract_products → generate_prices → clean_validate_and_load, daily, two retries, no catch-up. Note that DATABASE_URL is hardcoded in the DAG file rather than read from .env.
08

Read it

Two Metabase dashboard tabs over the same warehouse: one for whether the pipeline is healthy, one for what the prices say.

Under the hood
  • SQL lives in the repo Metabase stores its own cards in its own volume, which is not in git. dashboard/metabase_queries.sql is the source of truth for every query and names the chart type each card should use.
09

Stream the same prices

Everything above waits for a whole file, then processes it in one go. This route does the opposite: price events are written one small file at a time, and Spark picks each one up as it lands, appending to Delta tables — ordinary files on disk that keep a running log of every change, so a reader always sees a complete version rather than a half-written one.

python3 processing/streaming_prices.py --once
Under the hood
  • It needs Java, and it is the only stage that does This is real Spark, running local[2]. --once swaps every trigger to availableNow, so it drains whatever is already in data/stream/incoming and exits instead of running forever.
  • Three queries, three checkpoints One readStream feeds a Delta append of valid rows, a JSON quarantine of invalid ones, and a complete-mode latest-price aggregate, each with its own directory under data/stream/checkpoints. Deleting one checkpoint and not the others makes the outputs disagree on replay.
  • A ten-minute watermark The stream will wait up to ten minutes for a late event before it stops accepting events for that period, which is also what bounds the memory used for de-duplicating on event_id.
  • The rules are duplicated, not shared Validation here is a hand-written when chain plus a hardcoded KNOWN_STORES tuple. It does not import quality/semantic_validation.py. The same store list is hardcoded in five places: generate_stream_events.py, generate_prices.py, streaming_prices.py, price_expectations.py and tests/test_ingestion.py. A rule change has to be made in every copy.
10

Join the two routes

At this point the platform holds the same kind of data in two unrelated places: prices in the database, streamed prices in files. Neither can answer a question about the other. DuckDB opens both at once, which is the only thing that makes this one platform rather than two.

python3 -m serving.lakehouse
Under the hood
  • Nothing is copied delta_scan() reads the Delta Parquet files where they already sit, and the warehouse is attached with ATTACH … (TYPE postgres, READ_ONLY). There is no third copy of the data to keep in sync, and the join cannot write to the warehouse by accident.
  • The URL has to be rewritten postgres_dsn() exists only because DuckDB's postgres extension wants libpq keywords, not the postgresql:// URL that the rest of the project reads from .env.
  • Run it as a module python3 -m serving.lakehouse, not the script path. Same for python3 -m processing.inspect_delta, which prints the Delta tables back out.
  • The gold tables are a snapshot, the views are live lake_price_events and lake_latest_price are views over the Delta files and always reflect the latest stream output; the three gold_* tables are materialised at run time. Re-run this stage after any streaming run or the two will disagree.

Where the two routes disagree

The same 97 products were priced twice, once down each route. Ninety-four of them ended up in both. Asking what those two records say about the same product is the one question neither route can answer alone, and it is the reason the DuckDB stage exists.

305 events streamed

Across 97 products and all five stores, reduced to 208 latest-price rows — one per product and store, kept current as events arrive.

They differ by $3.16

Median gap between the two routes' average price for the same product. Only 13 of the 94 land within a dollar of each other, and 73 come out cheaper on the streaming side.

And it is not a bug

The two generators simply draw from different ranges: the batch one averages $10.51, the streaming one $8.10. The gap is invented, but the query that exposes it would find a real one the same way.

10

What this platform does not do

Stated plainly, because a reviewer will find them anyway.

Prices have no history

Every row in a run carries the same timestamp, so there is no trend to plot. Spreading event_timestamp across a date range in the generator would fix it.

One product category

The extract is filtered to beverages, so category has a single distinct value. Any chart grouped by category is one bar, which is why that card was removed.

Great Expectations is wired to nothing

The suites exist and are correct, but no code calls them. They need a runner and a place in the pipeline before they count as a validation layer.

Store differences aren't real

All five stores draw prices from the same distribution, so their averages sit within a few cents of each other by construction, not by finding.

Credentials in the DAG

DATABASE_URL is hardcoded in airflow_local/dags/smart_grocery_pipeline.py instead of coming from the environment.

The two routes check data separately

The streaming route does not use quality/semantic_validation.py. It re-implements the rules as a Spark expression, and the store list is hardcoded in five files. Nothing stops the copies from drifting apart, and no test would notice.

The streaming quarantine has never fired

Its rules work, but the stream generator injects no faults the way generate_prices.py does, so every event has passed. The quarantine folder holds 400 empty files and not one rejected record.
